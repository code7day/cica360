## ADR-001 — Stack frontend: Astro (SSG + islands)

| Campo | Valor |
|-------|-------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-20 |
| **Decisión** | El sitio público de CICA360 se construye en **Astro**, con salida estática (SSG), usando **islands architecture**: componentes `.astro` sin JS por defecto, y React o Preact **únicamente** en los bloques que necesitan interactividad real en el cliente (`contact_form`, y el slider del `hero` si hace falta JS real). No se usa una SPA de React puro ni Next.js. |
| **Contexto** | El sitio corre en un shared hosting **sin Node ni npm**, tiene que ser muy rápido/seguro/moderno y soportar alta demanda, y consume contenido de un CMS headless (Stamless) que se publica ocasionalmente, no que cambia por request. Se evaluaron 3 opciones: React puro (SPA), Next.js (static export), Astro. |
| **Alternativas consideradas** | (a) **React puro (SPA)** — descartado: renderiza todo client-side, paga el costo de un framework completo + hidratación en cada visita para contenido que es en su mayoría lectura estática; peor LCP/TTI y peor SEO sin trabajo adicional de prerender (que a su vez requeriría Node en alguna parte). (b) **Next.js con `output: 'export'`** — descartado: el modo estático de Next pelea contra el diseño del framework (sin Image Optimization API en runtime, sin API routes — que es justamente el mecanismo más simple para ocultar el Bearer del formulario —, pensado para correr con un servidor Node detrás, que es lo que este hosting no tiene). |
| **Consecuencias** | 1) El build (`astro build`) corre en CI o localmente, nunca en el servidor de producción — el hosting solo recibe el `dist/` estático. 2) Los bloques presentacionales del CMS (`rich_text`, `features`, `split`, `cta`, `logos`, `services_grid`, `testimonials`) se implementan como `.astro` sin directivas `client:*` — cero JS. 3) Solo `contact_form` (y opcionalmente el slider del `hero`) usa un island con React/Preact. 4) Un cambio de contenido en el backend (Filament) no se refleja en el sitio hasta el próximo build+deploy — trade-off aceptado de SSG, ver ARCHITECTURE.md §6 y la Fase 6 (post-MVP) para automatizarlo. 5) Este ADR resuelve el pendiente que el backend de Stamless tenía anotado en su propio `TASK.md` ("Elegir Astro vs Next.js") — la elección queda registrada acá porque es una decisión del proyecto frontend, no del backend. |

## ADR-002 — Estrategia del formulario de contacto: proxy PHP por defecto, token acotado como fallback

| Campo | Valor |
|-------|-------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-20 |
| **Decisión** | El submit de `POST /forms/contacto/submit` se resuelve, en orden de preferencia: (1) **Proxy PHP** — un script server-side (`contacto.php` o similar) subido junto al sitio estático, que recibe el POST del navegador, lo reenvía a Stamless con el Bearer guardado en config PHP (nunca en el bundle del cliente), y devuelve la respuesta. (2) **Token acotado** — si el hosting no soporta ningún scripting server-side, se usa un token de Console con **únicamente** la ability `forms:submit` (nunca `content:read`), aceptando que quede visible en el bundle del cliente, documentado explícitamente como excepción. |
| **Contexto** | Todo el contenido de lectura se resuelve en build time (el token nunca llega al navegador, gratis por ser SSG — ver ADR-001), pero el formulario de contacto se ejecuta en runtime, desde el navegador del visitante, después de que el sitio ya es HTML estático sin servidor propio. Hace falta una forma de que ese POST lleve el Bearer sin exponerlo. |
| **Alternativas consideradas** | (a) Poner el token completo (`content:read` + `forms:submit`) directamente en el JS del cliente — descartado de plano: expondría lectura de contenido con el mismo token, sin necesidad. (b) Depender de que el hosting soporte Node/serverless (ej. Cloudflare Workers/Pages Functions) para un endpoint propio — descartado como estrategia *por defecto* porque el requisito explícito es shared hosting sin Node; queda como alternativa a evaluar solo si el proxy PHP resulta inviable Y el fallback de token acotado no es aceptable para el cliente. |
| **Consecuencias** | 1) Casi todo shared hosting real (cPanel, Plesk, etc.) trae PHP + cURL habilitado aunque no traiga Node, así que el proxy PHP es la apuesta segura por defecto. 2) Si se termina usando el token acotado, el daño posible en caso de filtración queda acotado por diseño: `forms:submit` no permite leer contenido, y el endpoint ya tiene rate limiting del lado de Stamless (10 req/min por IP, además del general de 60/min) — y el token se puede revocar/regenerar desde Console (Desarrolladores → API Tokens → Regenerar) en segundos si hace falta. 3) La decisión final entre las dos rutas depende de confirmar las capacidades reales del hosting del cliente — ver `TASK.md`, Fase 3, subtarea #14, todavía pendiente. 4) Se agrega honeypot del lado del cliente como capa extra de anti-spam, independiente de que el backend (`Form.enable_honeypot`) todavía no lo aplique server-side. |
| **Actualización 2026-09-12 (cómo el proxy PHP obtiene su config)** | Pedido explícito del Tech Lead, a raíz de sumar `ipinfo.php` (ADR-004) con su propio token: "deberian leerlo [.env], asi centralizamos la configuracion de credenciales, si no estaremos con lo mismo duplicando variables y configuraciones". Hasta esta vuelta, "config PHP" (mencionado en la Decisión de arriba) significaba un `*.config.php` por proxy (`contacto.config.php`), gitignored, con `define()` — duplicando en la práctica los mismos valores que ya vivían documentados (sin uso real) en `.env`. Se retiran `contacto.config.php`/`contacto.config.example.php` y NO se crea el `ipinfo.config.php` equivalente que se había armado para ADR-004: ambos proxies ahora leen el MISMO `.env` en runtime, vía un lector minimalista nuevo (`public/_env.php`, sin dependencias — no hay `composer.json` en este proyecto Astro). Detalle de seguridad importante (ver docblock de `_env.php`): en producción, `.env` debe copiarse a mano UN NIVEL POR ENCIMA del document root (`dist/`) — igual que ya vivía en desarrollo local un nivel arriba de `public/` — nunca dentro de `dist/`/`public/`, porque a diferencia de un `*.config.php` (que un servidor PHP correctamente configurado ejecuta en vez de devolver como texto), un `.env` sí se sirve como texto plano si un visitante lo pide por HTTP, filtrando todas las credenciales. `STAMLESS_FORMS_PROXY_TOKEN`/`IPINFO_API_TOKEN` (ya documentadas en `.env`) pasan de ser referencia-únicamente a ser lo que `contacto.php`/`ipinfo.php` leen de verdad. |

## ADR-003 — Contexto de proyecto separado del backend Stamless

| Campo | Valor |
|-------|-------|
| **Estado** | Accepted |
| **Fecha** | 2026-08-20 |
| **Decisión** | Este proyecto (front de CICA360) tiene su propia carpeta, su propio `docs/context/` (`CURRENT_STATE.md`, `TASK.md`, `ARCHITECTURE.md`, `DECISIONS.md`, `PROGRESS.md`) y su propio manual del API Stamless (`docs/context/api/stamless-api-v1.md`, copiado/adaptado del `docs/api/v1.md` del backend), completamente separado del repositorio del backend Stamless. |
| **Contexto** | El backend Stamless (Laravel/Filament) y este front (Astro) son dos proyectos con stack, ciclo de vida y hosting distintos. Mezclar sus decisiones/ADRs en un solo `docs/context/` generaba confusión sobre qué regla aplica a qué proyecto — en particular, decisiones de dominio/rutas/excepciones del backend no tienen nada que ver con decisiones de framework/build/deploy del front. |
| **Consecuencias** | 1) Un agente trabajando en este repo no necesita (ni debe) leer el repo del backend para saber el contrato de datos — el manual en `docs/context/api/stamless-api-v1.md` es autosuficiente. 2) Si el contrato del API cambia del lado del backend (nuevo endpoint, cambio de envelope, nuevo `errors.code`), hay que actualizar ese manual acá — no queda sincronizado automáticamente, es responsabilidad manual documentada en `AGENTS.md`. 3) Decisiones de arquitectura del backend (dominios, `apiPrefix`, excepciones, etc.) siguen viviendo únicamente en el `DECISIONS.md` del repo de Stamless — no se duplican acá. |

## ADR-004 — Preselección de país por IP (proxy PHP `ipinfo.php`) + IP real del visitante reenviada a Stamless

| Campo | Valor |
|-------|-------|
| **Estado** | Accepted |
| **Fecha** | 2026-09-12 |
| **Decisión** | Nuevo proxy `public/ipinfo.php` — mismo patrón que `contacto.php` (ADR-002): el token de ipinfo.io nunca viaja a un bundle de cliente. Al montar, `ContactForm.tsx` llama a `detectVisitorCountry()` (`src/lib/api.ts`), que hace `GET` a ese proxy; si el `country_code` devuelto está en `COUNTRY_OPTIONS`, preselecciona el `<select>` de País (nunca pisa una elección manual del visitante, antes o después de que resuelva el fetch). El proxy solo devuelve `country_code` — nunca IP/ASN/nombre de proveedor al cliente, aunque el endpoint "lite" de ipinfo.io los incluya. Además, `contacto.php` ahora reenvía la IP real del visitante a Stamless vía header `X-Forwarded-For` (antes no lo hacía: al ser una llamada server-to-server, Stamless veía siempre la IP saliente del hosting de CICA360, nunca la del visitante) — ver ADR correspondiente del lado genesis (`FormSubmissionController::resolveClientIp()`, mismo día). |
| **Contexto** | Pedido del Tech Lead, compartiendo un ejemplo de la API "lite" de ipinfo.io (`GET /lite/{ip}?token=...` → `{ip, asn, as_name, as_domain, country_code, country, continent_code, continent}`) y sus credenciales demo en `.env`: "donde se podria usar el iso country_code ... para poder preseleccionar por default el pais al cargar la pagina, asi se ayuda, por usabilidad ... y asi de paso enviamos al api el IP para seguimiento tambien". |
| **Alternativas consideradas** | (a) **Llamar a ipinfo.io directo desde el navegador** — descartada: expondría `IPINFO_API_TOKEN` en el bundle de cliente (mismo problema de fondo que motivó el proxy de `contacto.php` en ADR-002), y además el navegador no conoce su propia IP pública sin un servicio externo (el propio ipinfo.io la infiere del origen de la conexión — solo funciona si la llamada la hace directamente el visitante, PERO exponer el token sigue siendo inaceptable). (b) **Resolver el país en build time** — descartada: la IP del visitante solo se conoce en runtime (request real del navegador), un sitio 100% estático no puede precomputar esto por visitante. (c) **Devolver el objeto completo de ipinfo.io al cliente** (IP/ASN/proveedor) — descartada: innecesario para el único uso (preseleccionar un `<select>`), y evitar exponer de más es más simple de razonar para privacidad. (d) **No cachear por IP en el proxy** — descartada: el plan de ipinfo.io tiene cuota; cachear 6h por IP (archivo en `sys_get_temp_dir()`, mismo mecanismo que el rate-limit de `contacto.php`) evita gastarla en recargas del mismo visitante sin necesitar Redis/Memcached (no disponibles en shared hosting). (e) **Un `ipinfo.config.php` propio** (mismo formato que tenía `contacto.config.php` antes de esta misma vuelta) — descartada de entrada: el Tech Lead pidió explícitamente centralizar credenciales en un solo lugar en vez de duplicarlas por proxy (ver la actualización de ADR-002 de este mismo día, que retira también el `contacto.config.php` preexistente) — ambos proxies terminan leyendo el mismo `.env` vía `_env.php`. |
| **Consecuencias** | 1) Archivo nuevo: `public/ipinfo.php` (lee su config vía `public/_env.php`, compartido con `contacto.php` — ver ADR-002, actualización 2026-09-12, para el detalle de ese mecanismo). 2) `.env`/`.env.example`: `PUBLIC_IPINFO_ENDPOINT` (default `/ipinfo.php`) + `IPINFO_HOST_SERVICE`/`IPINFO_API_TOKEN` (estas dos sí las lee `ipinfo.php` en runtime, a diferencia de las `PUBLIC_*` que solo lee el build de Astro). 3) `src/env.d.ts`: tipo de `PUBLIC_IPINFO_ENDPOINT`. 4) `src/lib/api.ts`: nueva `detectVisitorCountry()` — falla siempre en silencio (`null`), con timeout propio de 3s vía `AbortController`, nunca bloquea ni demora perceptiblemente el formulario. 5) `src/components/islands/ContactForm.tsx`: `useEffect` al montar + `countryTouchedRef` para no pisar una elección manual. 6) `public/contacto.php`: nuevo header `X-Forwarded-For` con la IP real ya calculada para su propio rate limit. 7) Lado genesis: `FormSubmissionController::resolveClientIp()` prioriza ese header sobre `$request->ip()` cuando viene y es una IP válida — ver PROGRESS.md/DECISIONS.md de ese repo, mismo día. 8) Sin runtime de PHP en este sandbox — balance de llaves/paréntesis/corchetes verificado vía script Python en los archivos PHP tocados/nuevos; `tsc --noEmit --ignoreDeprecations 6.0` sin errores. |
| **Actualización 2026-09-12 (country_code de origen SIEMPRE viaja al API)** | Pedido explícito del Tech Lead: "cabe la posibilidad abierta de que el cliente cambie de pais en el formulario pero siempre el api debe recibir el IP y country_code de origen, por favor asegurarse eso" — y, sobre si esto debía ser obligatorio del lado Stamless: "no requeridos de lado de stamless, sera opcion de cada cliente si desea usar". El GET de `ipinfo.php` al cargar la página (arriba) es solo UX best-effort — podía no haber corrido, fallar, o quedar "viejo" si el visitante después cambia el `<select>` de País a mano. Se extrae la lógica de consulta+cache a `public/_geoip.php` (`cica360_resolve_country_code(string $ip): ?string`, compartida) y `contacto.php` la vuelve a llamar DE NUEVO, siempre, en el momento mismo del submit, a partir de `$clientIp` (la conexión real, nunca nada del payload/navegador) — si resuelve, se manda como header `X-Origin-Country` a Stamless, junto a `X-Forwarded-For`. Completamente independiente del campo de negocio `country` que el visitante puede elegir a mano: ese sigue viajando tal cual, sin relación con este. Del lado genesis, `geo_country_code` es 100% opcional (no participa de ninguna validación de `FormField`, no es requerido para ningún tenant) — ver ADR correspondiente de ese repo, mismo día. |
| **Actualización 2026-09-12 (dominio declarado en `X-Forwarded-Host`, para que genesis valide el origen)** | Pedido del Tech Lead: "también validar que el formulario solo reciba de un dominio de la app (website cliente) que fue configurada al crear un token, por seguridad, creo que amerita que opinas?". Se le explicó la limitación real (esta llamada es server-to-server, `Origin`/`Referer` no son garantía criptográfica acá) antes de implementar. `contacto.php` declara su propio dominio público (host de `PUBLIC_SITE_URL` del `.env`) en el header `X-Forwarded-Host`, junto a `X-Forwarded-For`/`X-Origin-Country` — best-effort: si `PUBLIC_SITE_URL` no está seteado o no tiene un host parseable, el header simplemente no se manda, nunca bloquea el submit del lado de este proxy. **Corrección del mismo día, sobre cómo se interpreta este header del lado genesis**: la primera implementación (`FormSubmissionController::assertOriginIsAllowed()`, validando contra `Tenant::domains()`) quedó descartada — el Tech Lead aclaró que la protección real es a nivel de TOKEN de Stamless, no del tenant/sitio: "me refiero a stamless, la proteccion es para stamless, no para el sitio web, porque lo pueden usar solo con node o react o app... por eso tambien un select si es una web o es app desde donde se usará el api". El header que este proxy manda no cambia (sigue siendo el mismo `X-Forwarded-Host` con el dominio de CICA360), pero ahora lo lee `App\Http\Middleware\ValidateTokenOrigin` y lo compara contra el `allowed_origin` configurado en el TOKEN específico que usa este proxy (campo `platform = 'web'` en `App\Filament\Pages\ApiTokens`) — no contra una lista de dominios del tenant. Ver `genesis/docs/context/DECISIONS.md`, ADR-059 (ADR-058 queda `Superseded by ADR-059`). |

## ADR-005 — Animación de entrada sitewide: mecanismo estático `data-reveal` (reemplaza `properties.animation`, removido de Filament)

| Campo | Valor |
|-------|-------|
| **Estado** | Accepted |
| **Fecha** | 2026-09-17 |
| **Decisión** | Se implementa un mecanismo propio de animación de entrada al hacer scroll ("scroll-reveal"), estático y hardcodeado en este frontend — sin ningún control desde Filament/Studio. Base: atributo `data-reveal="up"|"fade"` en el elemento a animar (+ `style="--reveal-delay: Nms"` opcional para stagger) + reglas CSS en `src/styles/global.css` (`opacity`/`transform` iniciales, transición, override completo bajo `prefers-reduced-motion: reduce`) + un único `IntersectionObserver` global en `src/layouts/BaseLayout.astro` que agrega `.is-revealed` la primera vez que el elemento entra en viewport y luego deja de observarlo (reveal-once, no repite en cada scroll). Cableado en los 18 componentes de `src/components/blocks/`, en `src/pages/servicios/[slug].astro` (excepto la sección de header/wave/banderas, fuera de alcance por instrucción explícita del Tech Lead) y en `src/pages/blog/index.astro`/`src/pages/blog/[slug].astro`. |
| **Contexto** | Pedido original: usar el selector "Animación de entrada" (`properties.animation`) ya presente en Filament para setear una animación inicial vía seeder. Investigación previa confirmó que ese campo era 100% fantasma — nunca consumido por ningún componente `.astro` de este sitio pese a estar declarado desde el MVP. Al preguntarle al Tech Lead el alcance exacto, la respuesta cambió la tarea por completo: "quitar ese campo desde filament, que ya no lo tenga, y solo de forma estatica cada cliente o desarrollador implementara la animación... tenemos que aplicar animacion en todos los componentes de cada seccion y en todas las paginas de todo el sitio, para que se vea mas moderna, que la animacion sea coherente, suave, sutil, amigable y elegante". Ver ADR-070 en `genesis/docs/context/DECISIONS.md` para la remoción del lado Filament. |
| **Alternativas consideradas** | (a) **Conectar `properties.animation` a un motor real de reveal**, respetando el valor elegido por bloque desde Studio — descartada explícitamente por el Tech Lead a favor de un mecanismo fijo por frontend, sin exponerlo como opción editable (evita que un tenant desactive/rompa la coherencia visual del sitio combinando distintas animaciones por bloque). (b) **Instalar una librería JS de scroll-reveal** (AOS, GSAP ScrollTrigger, framer-motion, etc.) — descartada: viola ADR-001 de este repo ("JS mínimo... sin dependencias") y el sitio ya tiene un patrón vainilla establecido para interactividad puntual (`initHeroSliders()` en `Hero.astro`, `initServiceTabs()` en `[slug].astro`); un solo `IntersectionObserver` reusado por toda la página cubre la necesidad sin librería nueva. (c) **CSS `@scroll-timeline`/`animation-timeline: view()`** (scroll-driven animations nativas) — descartada por soporte de navegador todavía insuficiente para un sitio público en 2026 sin fallback aceptable. |
| **Consecuencias** | 1) `src/styles/global.css`: nuevas reglas `[data-reveal]`/`.is-revealed` (2 variantes: `up` con `translateY`, `fade` solo opacidad) + `--reveal-delay` como custom property para stagger en listas/grids, dentro del `@layer base` existente. 2) `src/layouts/BaseLayout.astro`: nuevo `<script>` (Astro-procesado, no `is:inline`) con el `IntersectionObserver` global, documentado con referencia cruzada a `global.css`. 3) Cableado extensivo en `src/components/blocks/*.astro` (18 archivos) vía el partial compartido `BlockHeading.astro` (cubre pretitle/título/subtítulo de 4 bloques a la vez) + wiring directo en el resto — texto/listas/CTAs con `up` y stagger, imágenes/media sueltas con `fade`. `Hero.astro` y `Heading.astro` (banners siempre visibles desde el primer render de su página, "above the fold") quedan deliberadamente SIN `data-reveal` — `Hero.astro` además ya tiene su propio sistema de animación de entrada por slide (`hero-anim-play`/`data-hero-anim`, decisión previa de 2026-08-30, no tocado). El carousel de `Features.astro` (GSAP scroll-pin horizontal) tampoco lleva `data-reveal` en sus tarjetas para no interferir con ese mecanismo ya existente — sí lo lleva su heading compartido. 4) `src/pages/servicios/[slug].astro`: cableado en intro, tabs (botones + paneles + items de listas/acordeón con stagger), "¿Por qué elegirnos?" y "tip" — la sección de header/wave/banderas NO se tocó, por instrucción explícita del Tech Lead ("no edites nada, que ya fue resuelto con otro agente"). 5) `src/pages/blog/index.astro`/`blog/[slug].astro`: cableado en título, listado con stagger, imagen destacada y cuerpo del post. `src/pages/index.astro`/`src/pages/[slug].astro` no necesitan cableado propio — son 100% block-driven, ya cubiertos por el trabajo en `blocks/`. 6) Interfaces TS locales `animation?: 'none' \| 'fade' \| 'slide-up'` (huérfanas, documentadas como "sin consumidor real"/"campo fantasma") removidas de `ServicesGrid.astro`, `TestimonialsGrid.astro`, `Split.astro`, `Features.astro`, `Testimonials.astro`; comentario de `ImageBlock.astro` actualizado (antes decía "campo muerto en TODO el proyecto", ahora refleja que el campo fue removido de raíz). 7) Verificado con `@astrojs/compiler` `parse()` (0 diagnósticos por archivo) y `tsc --noEmit --strict --ignoreDeprecations 6.0` (limpio). 8) **No se hizo `git commit`/`push` ni build/deploy** — constraint explícito del Tech Lead para todo este trabajo: "al terminar no desplegar ni guardar a git, solo quiero probar en local". El siguiente agente no debe deployar esto sin pedido explícito. |

## ADR-006 — Fase 6 (post-MVP) adelantada: deploy automático por webhook

| Campo | Valor |
|-------|-------|
| **Estado** | Accepted |
| **Fecha** | 2026-09-17 |
| **Decisión** | El paso a producción deja de ser manual: `.github/workflows/build-and-deploy.yml` gana un trigger `repository_dispatch` (`types: [content-updated]`) y el paso `SamKirkland/FTP-Deploy-Action` (antes comentado, "no en uso") pasa a correr siempre, subiendo `dist/` automáticamente al hosting vía FTP tras cada build. Genesis (backend headless) dispara ese evento cuando se guarda contenido del tenant CICA360 — ver ADR-072 en `genesis/docs/context/DECISIONS.md` (`FrontendDeployService`/`TriggerFrontendDeploy`/`DeployTriggerObserver`). El artifact `cica360-dist` se mantiene como respaldo/rollback manual. Requiere los secrets `FTP_SERVER`/`FTP_USERNAME`/`FTP_PASSWORD` configurados en este repo (Settings → Secrets and variables → Actions) — fuera del alcance de este ADR (credenciales, nunca en código). |
| **Contexto** | ADR-001 (punto 4 de sus consecuencias) ya dejaba anotado el trade-off: "un cambio de contenido en el backend no se refleja en el sitio hasta el próximo build+deploy... ver la Fase 6 (post-MVP) para automatizarlo". El 2026-09-13 se decidió EXPLÍCITAMENTE mantener ese paso manual mientras el contenido cambiara seguido (pre-lanzamiento, control fino de cuándo sale cada versión). El 2026-09-17 el Tech Lead confirmó en producción que esa fricción rompía la expectativa básica de un CMS headless: editó el título de la Home (agregó una "X") y la website siguió mostrando el contenido viejo — "no funcionaría entonces el CMS headless". Se le presentaron 3 estrategias (fetch en cliente/0 delay, webhook con rebuild automático/~1-3 min, híbrido) y priorizó explícitamente mantener SEO/performance intactos por sobre la latencia cero. |
| **Alternativas consideradas** | Ver ADR-072 (genesis) — la decisión se tomó una sola vez, evaluando ambos lados del sistema a la vez, y se documenta espejada en los 2 repos porque cada uno tiene su propia mitad de la implementación (genesis dispara, cica360 escucha y despliega). |
| **Consecuencias** | 1) `on.repository_dispatch.types` en el workflow debe seguir coincidiendo EXACTO con `FrontendDeployService::EVENT_TYPE` (`content-updated`) del lado genesis — un rename futuro de cualquiera de los 2 lados rompe el disparo en silencio (el workflow simplemente nunca se dispara por este medio, sin error visible) si no se actualiza el otro en el mismo cambio. 2) El deploy YA NO es "control manual explícito de cuándo sale cada versión" (la decisión de 2026-09-13) — cualquier guardado en Studio para un tenant con el webhook configurado publica solo, sin gate humano. Si en algún momento se necesita volver a pausar publicaciones automáticas (ej. una ventana de mantenimiento), la palanca es `Tenant::deploy_repo`/`deploy_token` en genesis (poner cualquiera en `null` desactiva el disparo sin tocar este workflow) — no hay pausa del lado de este repo. 3) El artifact de respaldo (`cica360-dist`) sigue subiendo en cada run — sirve de rollback manual si el FTP automático fallara o si hiciera falta revertir una versión sin esperar un nuevo build. 4) Cero cambio a Astro/SSG/islands — el sitio sigue siendo 100% estático, este ADR solo automatiza QUIÉN dispara el build, no CÓMO se renderiza. |
